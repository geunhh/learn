PaperTutor 배포 파이프라인

코드가 main에 들어간 뒤 dev를 거쳐 prod에 올라가기까지의 경로와, 그 과정에서 GitHub Actions가 AWS에 들어가는 방법(OIDC)을 2026-10-01 실제 배포 기록으로 정리했다.

왼쪽은 자동, 오른쪽은 사람이 버튼을 누른다. 가운데 보관소가 두 세계를 잇는다.

2. dev 배포 자동

레포 세 곳에 워크플로가 하나씩 있다. main에 push되면 돌고, 끝나면 그 커밋 SHA 이름으로 산출물이 남는다.

Deploy BE (dev) app

  • 트리거: main push, be/** 변경 시
  • Gradle 빌드 → 이미지 → dev ECR push (태그 SHA)
  • 현재 task definition 복제, 이미지만 교체 → 새 revision → 서비스 갱신 → 안정화 대기
  • Role: papertutor-dev-app-deploy

Deploy FE (dev) app

  • 트리거: main push, fe/** 변경 시
  • Vite 빌드 → dist/
  • tar로 산출물 버킷에 보관 (같은 SHA면 건너뜀)
  • dev S3 sync → CloudFront 무효화

Deploy AI (dev) ai

  • 트리거: main push 전부
  • 이미지 하나 → dev ECR push
  • api·parser-worker·compile-worker 3개 서비스에 같은 이미지로 배포
  • Role: papertutor-dev-ai-deploy

왜 tar를 따로 보관하나. BE·AI는 ECR에 이미지가 남지만 FE는 S3에 파일을 뿌리고 끝이라 "그때 빌드한 결과"가 남지 않았다. prod가 재빌드 없이 같은 것을 쓰려면 보관소가 필요했다. (YMC-399)

롤백

전용 워크플로가 없다. 같은 워크플로에 이전 SHA를 넣으면 된다. 이미지가 prod ECR에 이미 있으면 복사를 건너뛰고 revision만 새로 등록한다. BE는 Flyway가 기동 시 돌기 때문에 마이그레이션이 expand/contract를 지켰을 때만 되돌릴 수 있다.

4. OIDC: 워크플로가 AWS에 들어가는 방법 인증

워크플로는 GitHub 서버에서 돌면서 AWS의 ECR·ECS·S3를 조작해야 한다. 예전 방식은 AWS 액세스 키를 발급해 GitHub Secrets에 넣는 것인데, 영구 비밀번호라 유출되면 끝이고 주기적으로 바꿔야 한다. OIDC는 저장된 비밀번호 없이 매 실행마다 임시 자격을 받는 방식이다.

아래 단계를 누르면 그림의 해당 화살표가 강조된다.

  1. 1
    워크플로가 GitHub에 토큰을 요청한다
    워크플로 파일의 permissions: id-token: write가 이 요청을 허용한다.
  2. 2
    GitHub가 서명된 토큰을 준다
    토큰 안에 "이 실행은 repo:team-ymc/infra:ref:refs/heads/main에서 왔다"가 적혀 있고 GitHub의 서명이 붙어 있다. 위조하면 서명이 깨진다.
  3. 3
    워크플로가 AWS에 Role을 맡겠다고 한다
    aws-actions/configure-aws-credentials가 토큰과 Role ARN을 STS에 보낸다.
  4. 4
    AWS가 서명을 검증한다
    계정에 등록된 OIDC provider가 "GitHub의 서명을 믿는다"는 설정이다. 발급처 URL마다 하나만 등록할 수 있다.
  5. 5
    Role의 신뢰 조건과 맞으면 임시 자격을 준다
    Role의 신뢰 정책에 "infra 레포 main 브랜치만"이 적혀 있다. app 레포에서 온 토큰으로는 이 Role을 못 맡는다. 자격은 1시간 뒤 만료된다.
  6. 6
    임시 자격으로 AWS를 조작한다
    Role의 권한 정책에 적힌 것만 된다. prod 배포 Role은 dev ECR 읽기, prod ECR 쓰기, prod ECS 갱신, 버킷, CloudFront 무효화까지다.

provider와 Role의 역할 분담

provider 발급처 신뢰

  • "token.actions.githubusercontent.com의 서명을 믿는다"
  • 계정에 하나. dev·prod가 공유
  • bootstrap Terraform이 소유

Role 직책

  • 신뢰 정책: 누가 맡을 수 있나 (레포·브랜치)
  • 권한 정책: 맡으면 뭘 할 수 있나
  • 용도마다 하나. dev app, dev ai, prod deploy
Role맡을 수 있는 곳할 수 있는 것
papertutor-dev-app-deployteam-ymc/app maindev ECR backend 쓰기, dev BE 배포, dev FE 버킷, 산출물 버킷 fe/* 쓰기
papertutor-dev-ai-deployteam-ymc/ai maindev ECR ai 쓰기, dev AI 서비스 3개 배포
papertutor-prod-deployteam-ymc/infra maindev ECR 읽기, prod ECR 쓰기, prod ECS 4개 갱신, PassRole, 산출물 버킷 읽기, prod FE 버킷, CloudFront 무효화

왜 prod Role을 infra 레포에 묶었나. app·ai 레포 코드가 아무리 바뀌어도 prod에는 손댈 수 없다. prod를 바꾸는 건 infra main에서 사람이 실행한 워크플로뿐이다.

5. Terraform 구성과 state

Terraform은 "이런 자원이 있어야 한다"는 코드와, "내가 만든 자원이 AWS에서 어떤 ID를 가졌나"를 적은 장부(state)로 동작한다. 코드에 있고 장부에 없으면 만들고, 코드에 없고 장부에 있으면 지운다. 이 마지막 줄이 위험한 지점이다.

infra에는 묶음(root)이 세 개 있다. OIDC provider는 원래 dev 묶음에 있었는데, prod도 같은 provider가 필요해서 공용 자리인 bootstrap으로 옮겼다.

bootstrap

장부: 로컬 파일 (사용자 PC)
  • Terraform 장부 S3 버킷
  • FE 산출물 버킷
  • GitHub OIDC provider

dev

장부: S3 papertutor/dev/…
  • VPC·ECS·RDS·ALB… dev 전부
  • GitHub OIDC provider
  • provider 조회 (data)
  • dev app·ai 배포 Role

prod

장부: S3 papertutor/prod/…
  • VPC·ECS·RDS·ALB… prod 전부
  • provider 조회 (data)
  • prod 배포 Role

AWS는 그대로, 장부만 옮기기

코드에서 provider 블록을 dev에서 빼고 bootstrap에 넣은 뒤 그냥 apply하면, dev는 "코드에 없다"며 provider를 지우고 bootstrap은 "새로 만든다"며 실패한다. 그 순간 dev 배포가 끊긴다. 그래서 장부만 직접 고쳤다.

순서명령기대 결과
1bootstrap: terraform importbootstrap 장부에 기존 provider 등록. AWS 변화 없음
2bootstrap: terraform plan태그만 1건 변경 (dev 태그 → bootstrap 태그)
3dev: terraform state rmdev 장부에서 기록만 삭제. AWS 변화 없음
4dev: terraform planNo changes
5bootstrap: terraform apply태그 갱신
6prod: terraform applyRole·정책 2개 추가, 기존 자원 변경 없음

import를 먼저 하는 이유는 "어느 장부에도 없는 순간"을 만들지 않기 위해서다. 잠깐 두 장부에 같이 있는 건 안전하지만, 어디에도 없으면 실수로 apply했을 때 새로 만들려다 실패한다.

6. 올릴 SHA는 어떻게 고르나

산출물 이름은 main에 push된 커밋의 SHA다. 우리는 PR을 merge 커밋으로 합치기 때문에, 파일을 실제로 고친 커밋과 main에 push된 커밋이 다르다.

git log -1 -- fe/는 왼쪽 위 커밋을 돌려주고, 그 이름의 tar는 없다. 그래서 runbook은 git 명령 대신 app·ai 레포 Actions의 dev 배포 실행 이력에서 성공한 실행의 커밋을 고르라고 안내한다. 산출물 버킷의 tar 이름이나 dev ECR 태그를 직접 봐도 같은 답이다. 없는 SHA를 넣어도 verify가 걸러 준다.
